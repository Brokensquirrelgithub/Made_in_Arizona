# Host PC co-op playtest

Co-op supports one host and up to three guests. The host PC runs vehicle physics, enemies, damage, pickups, world exploration, missions, and saving. Guests send driving and combat inputs and render the host's world state. The session uses Unity Relay and an invite code, so players do not need to forward a router port.

## Unity Services setup

This repository is linked to the Made in Arizona Unity Cloud project (`77d063f5-15d6-4012-b5fa-7025d9caeb87`). Sign into a Unity account with access to that project when building in Unity 6000.5.5f1. Enable Relay / listen-server networking for the project in the Unity Dashboard. Build all PCs from the linked project so they share the same Unity project ID and game code. See [Unity's project-link instructions](https://docs.unity.com/en-us/services/getting-started) and [Relay with Netcode for GameObjects](https://docs.unity.com/en-us/mps-sdk/tutorials/relay-and-ngo).

The project pins `com.unity.netcode.gameobjects` 2.13.3 and `com.unity.services.multiplayer` 2.3.2, compatible with this Unity editor. Services sign in anonymously when players choose Host or Join. The menu displays a service or transport error if connection setup fails.

## Play

1. On the host PC, open **Co-op** on the main menu and choose **Host Co-op**. The host's garage opens; click the co-op badge to copy the join code.
2. On each guest PC, enter that code on the main menu and choose **Join Host**. Each guest's garage opens so they can choose their car, weapon and parts from their own save. The other players' selected vehicles park beside the local car in every player's garage, with numbered labels. Changing cars or paint updates the parked display for everyone.
3. The host chooses the mission. Each player presses **Ready** in the garage. When every connected player is ready and guest loadouts have arrived, a five-second countdown starts. Changing a loadout or mission cancels readiness. Everyone then appears in the host's world. The host's campaign save determines world progress.
4. The host controls retry, regeneration, and returning to the garage. Guests can view the map and pause their own controls; only the host may craft upgrades or change the world. The host can copy the code from the main menu and sees it while driving.

## Co-op playtest tuning

Open **Pause → Dev Tuning / Mouse** while playing. **Combat** changes world balance, including enemy health, and only the host can edit it. **Impact damage to props** on the Driving tab is also host controlled. **Camera**, **Light & Color**, **Reflections**, and **Dirt & Sky** affect local presentation and remain editable on each PC. Personal graphics, audio output, and input preferences also remain local.

**Driving**, **Drift**, and **Engine** are saved as profiles for the current car. **Slot 1** tunes the equipped garage weapon; **Slot 2** tunes an equipped field weapon. Weapon tabs expose damage per hit, shots per second, projectile speed, and blast radius when that weapon has one. Car and weapon changes apply during play and sync to everyone using the same item.

If players share a car or weapon, one player owns its tuning sliders for the session. The host owns any item they use. Otherwise, the first guest who joined among players using that item owns it. Everyone else sees the shared item's controls locked and receives the owner's values. A guest using a unique car or weapon keeps control of that item's tuning.

Co-op tuning is a draft until the host chooses **Leave Co-op**. The host then chooses **Save Defaults** or **Discard** once for all players. Save makes the current tuning each player's local default; guests adopt the host's world-balance values, and players sharing a car or weapon save its owner's winning profile. Discard restores every player's pre-session tuning. Campaign progress can still save during the session. A guest who leaves early, or a session that ends unexpectedly, discards that player's draft.

The code works while the host is connected to Relay. Closing the host ends the session. All players should use the same build; the world protocol rejects incompatible versions. Relay availability and usage are subject to the linked Unity project's service settings.

The co-op badge shows a live round-trip ping sampled once per second. Guests see their ping to the host; hosts see one value per connected guest. A missing or stale reply shows `--`. The value is smoothed for readability and includes the Relay route. It is useful for noticing sustained delay during ordinary play; use `coopbench` below for packet delivery, jitter, frame timing, and synchronized driving logs.

## Capture a co-op driving trace

During a sortie, any player can open the dev console with **F5** and enter `cooplog`. Each machine continuously keeps a rolling 20-second in-memory timeline; the command saves the preceding 15 seconds from every connected player, including the lead-up to the problem. The host initiates one capture ID and collects a copy of every guest's trace in its `CoopDiagnostics/<capture ID>` folder under the game's persistent data directory. Each guest also keeps its own copy. `cooplog path` displays the local folder; the console prints each saved or collected file path. The host folder's `manifest.txt` lists which guests have arrived or are still pending. Captures stay on disk until manually removed.

The CSV files use the co-op server clock for comparison. Physics rows record each player's car position, velocity, yaw, and input sequence on every physics tick. Input send/receive and snapshot send/receive rows show packet timing, acknowledged input, the host position in the snapshot, the guest's position and yaw error before correction, and how many buffered movement steps were replayed. This is a lightweight diagnostic timeline; it does not record graphics, audio, or a full replay. Guest uploads happen after the trigger in small compressed chunks so the rolling recorder itself adds no network traffic.

Run `python Tools/analyze_coop_trace.py "<host capture folder>"` to print each guest's median, 95th percentile, and largest position difference against interpolated host physics, plus input and snapshot transit and pre-correction error. The script matches input sequences and snapshot ticks to estimate clock offset first. It assumes similar median delay in both directions, so timing and position differences remain estimates.

## Benchmark a live co-op session

During a sortie with at least two connected players, open **F5** and enter `coopbench` on the host or any guest. The host starts a 12-second probe on every connected machine. Each machine sends small unreliable packets to its peer(s) at 20 Hz, and the receiver echoes them. This measures delivered packets and round-trip delay in both directions without changing vehicle controls. Two seconds after probes end, the host triggers the same synchronized trace upload used by `cooplog`. Use `coopbench path` to find the local copy. The host's capture folder contains its own CSV, every received guest CSV, a `manifest.txt` that shows any guest still pending, and a `benchmark-report.txt` that updates as uploads arrive. Keep playing during the probe to include real driving, combat, input, snapshot, and correction data.

Run `python Tools/analyze_coop_trace.py "<host capture folder>"` for host-to-guest and guest-to-host delivery counts, round-trip median and 95th percentile, 95th percentile round-trip variation, and each machine's frame-time spikes alongside the driving comparison. Missing probe datagrams and missing guest uploads are reported separately. The benchmark uses the current route through Relay, so repeat it under the network conditions that produced a problem. Results measure application-level delivery and delay during this sample; they do not isolate Relay from the local network or PC performance.

The host report marks the capture complete only after every connected player's trace contains a full probe window, driving input, snapshots, and both send/receive directions. It lists each guest's frame-time and correction-error p95. Attention flags call out more than 5% probe loss, RTT p95 above 250 ms, frame p95 above 50 ms, or correction error p95 above 2 m; these are screening thresholds, not a diagnosis. For a controlled one-PC Relay smoke test, launch the existing `-miaCoopBenchHostTest` and `-miaCoopBenchGuestTest` players with `-miaSmokeTest` and a shared `MIA_COOP_CODE_PATH`. Set `MIA_COOP_EXPECTED_PLAYERS=3` and launch two guest processes to check multi-guest collection.

The connected-player smoke run has passed with one host and three guests on a single PC: all four logs arrived under one capture ID and the host report was complete. This verifies collection and report assembly; a test across separate machines and networks is still needed to characterize real-world jitter.

## Implementation and playtest status

The host sends car, pickup, mission, projectile, explosion, prop-break, and discovered-map-pin updates. Player cars update at 20 Hz and other cars at 10 Hz. Guests predict their own driving with local physics. Each host acknowledgment selects recent locally simulated movement tagged with input sequences; the guest replays that movement from the host snapshot and eases any remaining error. This is a movement replay rather than a second Unity physics simulation, since collisions and suspension can differ between machines. The guest camera keeps its own follow anchor and eases physics corrections separately. Other cars predict between snapshots using host velocity and yaw rate. Car snapshots use a compact binary format so they fit the unreliable delivery limit; they also carry the last input sequence applied by the host, turret aim, nitro state, warning zones, rally state, each car's death-ray beam, washing-machine flail head and the car on its tow-hook cable. Teammates appear as Player 1–4 waypoints on the HUD and map. Bowling-ball launches, mirror dust, rally horns, repair impacts and area strikes are sent as one-off effects. Shoulder reverse and nitro-on-A are each player's own control settings: guests send their reverse button and mode with their inputs. This is co-op protocol 11; all players need the same build. Guest inputs are clamped on the host; guest physics is visual prediction only, while host damage, patrol spawning, exploration, and saves remain authoritative. Objective proximity, interaction, enemy targeting, supplies, and discoveries include all live player cars. Late joiners generate the host's world config and receive the current pin state and broken-prop history after loading. A player whose car is destroyed watches a surviving teammate until the host ends or restarts the mission.

Earlier live Relay sessions connected a host and three guests with distinct and duplicate car and weapon loadouts; all three guest cars drove from remote inputs. Three-player sessions checked both Save Defaults and Discard, including shared-item ownership, unique guest tuning, and host-to-guest decision delivery. A separate session let a guest join a generated campaign after it started and verified driving and a previously discovered map pin. After local driving prediction was added, the Windows player build passed the snapshot and motion smoke checks, and a separate host and guest process both passed the Relay garage lobby check; the guest car was confirmed dynamic and locally predicted. These checks ran on one PC. Multi-PC playtesting is still needed for latency, reconnect/disconnect, and visual fidelity. Projectile replication recreates ordinary round visuals; unusual field ordnance and transient weather effects may still look different on guests. The guest camera follows the locally predicted car; physics differences around collisions and host-only effects can still require visible correction.

The garage lobby was also tested with separate host and guest players over Relay on one PC: the guest selected a Juniper, both players readied, the countdown launched mission 1, and the host spawned the guest's selected car. Both players resolved the other's Player 1–2 marker. The snapshot smoke check verifies turret aim serialization and the guest nitro glow.
